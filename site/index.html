Your help center goes stale the day you ship. KIRA reads your code instead.

KIRA turns a codebase into a maintained knowledge base about your product, then answers your users' questions from it — in their language, grounded in what the code actually does, and never invented.

The wedge

Docs drift. Code can't.

Every in-product help assistant on the market is grounded in documentation — help-center articles, support tickets, marketing pages. All of it describes the product as it was the last time somebody wrote it down. Source code cannot describe a product it does not build.

That is the whole thesis, and everything else in KIRA exists to make it trustworthy enough to put in front of a paying customer.

route

It knows where things are

Routes come out of your router, so a fact can carry the path it lives at. The assistant hands the reader a working link instead of describing where to click — and it knows that the same question means different things on different screens.

requires

It knows who can see them

When the code gates something behind a plan or a role, the fact carries that gate. Telling a Free user how to use a Business feature is worse than silence, and no article has a field for this.

boundary

It knows what you can't do

Code is full of guards, plan checks and unsupported branches. The costliest wrong answer in this category is not an invented feature — it is a confident yes to something the product refuses. So refusals are a first-class fact type.

git

It leaves a paper trail

Every fact records the files it came from, the commit, and the model that wrote it. Knowledge lives in your repo, so "what do we now tell users" is a git diff, and nothing reaches a customer without review.

Pipeline

How it works

Four stages. Each one is independently useful, and each has its own command.

kira init

Propose the map

Scans the repo and proposes an area per user-facing page and per behaviour module, deriving routes from the router. You edit it — an area is a topic someone asks about, not a directory.

kira extract

Read the code

Reads each area and writes what it means for the people who use the product. Incremental: an area whose sources have not changed is skipped entirely.

kira ask

Answer from facts

Retrieves, filters by who is asking and where they are, and answers from the retrieved facts only — with an honest "I don't have that" when they don't cover it.

kira eval · v0.2

Prove it

Generates questions per area, answers them through the real pipeline, judges the answers, and turns the weak ones into a documentation backlog.

Getting started

Install & quickstart

Five minutes from clone to first answer. No database, no vector store, no second API key.

  1. Install and authenticate

    $ npm install -g kira-knowledge
$ export ANTHROPIC_API_KEY=sk-ant-…

    The SDK also accepts ANTHROPIC_AUTH_TOKEN or a profile from ant auth login.

  2. Look at the areas it proposes

    $ kira init --dry-run

    Writes nothing. Prints one row per proposed area with the route it derived, so you can see whether the map makes sense before anything is generated.

  3. Write the config, then edit it

    $ kira init
$ $EDITOR .kira/config.yaml
    This is the ten minutes that matter. The area map is the highest-value human input in the system. Merge what belongs together, delete what has nothing user-facing, and give each area a name your users would recognise.

  4. Extract

    $ kira extract
› domains — 6 files, 2 batch(es), end_user
›   batch 1/2 → 12 fact(s)
✓ domains — 21 fact(s) written

    Facts land in .knowledge/. Commit them: the pull request is where a human approves what a customer will read.

  5. Ask

    $ kira ask "how do I connect a domain I already own?"

    The answer streams to stdout and everything else to stderr, so kira ask … 2>/dev/null gives you just the answer.

Reference

The knowledge format

One fact per file at .knowledge/<area>/<slug>.md: YAML frontmatter, then the answer in markdown. Plain files, so they diff, review, and travel like any other source.

---
id: domains/connect-existing
area: domains
type: workflow            # feature · workflow · concept · ui_location
audience: end_user         # faq · boundary · policy · troubleshooting
title: Connect a domain you already own
summary: Point an existing domain at your project from project settings.
route: /project/:id/domains  # dynamic segments as :name
requires:
  plan: [pro, business]     # gated away from readers who can't reach it
sources:                     # the audit trail
  - src/app/project/[id]/domains/page.tsx
extracted:
  at: 2026-08-18
  model: claude-opus-5
  area_hash: 4f1c9a…        # drives staleness detection
  git_sha: a3f9c21
confidence: high            # low is quarantined from answers
---
Open **Project settings → Domains**, choose **Add existing domain**, and enter
the domain name. Copy the two DNS records shown and add them at your registrar…

Fact types

TypeWhat it holds
featureA capability that exists.
workflowAn ordered way to accomplish something.
conceptA term or model the reader needs in order to use the product.
ui_locationWhere something lives in the interface.
faqA question users actually ask, with its answer.
boundarySomething the product does not or cannot do, and the alternative if one exists.
policyA rule that affects the reader: limits, quotas, retention, billing behaviour.
troubleshootingA symptom, its likely cause, and what to try next.
Reference

Configuration

.kira/config.yaml is written by kira init and then edited by you. Everything except areas has a working default.

version: 1

assistant:
  name: KIRA                # rename it per deployment
  audience: end_user        # end_user · operator · developer
  language: mirror         # answer in the reader's language

knowledge:
  language: English        # what the facts are written in

models:
  extract: claude-opus-5
  answer: claude-opus-5
  judge: claude-opus-5

effort:                     # how hard the model works per stage
  extract: high            # a durable artifact, nobody waiting
  answer: medium           # a person is watching a cursor blink
  judge: high

areas:
  - id: domains
    name: Custom Domains
    audience: end_user
    route: /project/:id/domains
    paths:
      - src/app/project/[id]/domains

Under the hood

How a question finds a fact

A knowledge base is hundreds of facts, not millions of documents, and every fact carries a hand-quality title and summary. So retrieval is BM25 — no embeddings, no vector store, nothing to run. It costs nothing, works offline, and returns the same result twice, which matters more than marginal recall when the output is customer-facing.

  • Rewrite. The question is rewritten into the language the facts are written in. Lexical retrieval cannot cross languages: a Russian question against an English base scores exactly zero, and the assistant honestly reports ignorance about something it knows.
  • Score. BM25 over title (×3), summary (×2) and body.
  • Place. Facts matching the reader's current screen are boosted — multiplicatively, so this reorders comparable matches instead of lifting an irrelevant one.
  • Gate. Facts requiring a plan, role or flag the reader lacks are dropped. An unknown reader is never gated, because that would make an unauthenticated widget answer less than it knows.
  • Audience. A developer-facing fact never reaches an end user.
  • Confidence. Anything the extractor flagged low stays out unless you ask for it.
  • Diversity. Near-duplicates are rejected, so five slots hold five distinct facts rather than one fact restated five times.

Optional embeddings arrive in v0.2 as a hybrid layer for large bases — exactly where BM25 starts to hurt, and not before.

Where this is

Status & roadmap

KIRA is v0.1 and honest about it. The extraction and answering path works end to end on real repositories; the parts that make it safe to show a customer are still ahead.

v0.1working now

Extract, retrieve, answer

init, extract, status, ask. Files only, BM25 only, no infrastructure. Good enough to run in CI and use from a terminal — inside your team.

v0.2next

The eval loop

Generated questions per area, plus cross-area and deliberately out-of-scope ones — because a system that cannot say "I don't know" scores well on coverage and fails in production. An independent judge scores every answer; weak ones become a gap backlog. Plus the Batch API for full rebuilds and optional embeddings.

Until this exists there is no way to tell "answers well" from "answers confidently". That is the gate before anyone outside the team sees an answer.

v0.3planned

The widget

An HTTP endpoint over the same answering path, a React component and a script tag, the reader's screen and plan passed in as context, working deep links, and one adapter for handing a conversation to a human.

v0.4planned

Production shape

Optional Postgres and pgvector backend, atomic knowledge versions so a deploy is a switch rather than a race, multi-tenancy, and analytics over the gap backlog.

Deliberately out of scope

  • Not a coding assistant. Claude Code, Cursor and friends already answer a developer's questions about a repository, and an agent with grep beats naive retrieval at that job. KIRA's reader cannot open the code.
  • Not an agent that acts inside your product. An assistant that clicks things on a customer's behalf is a different product with a different risk profile.
Before you adopt it

Honest limits

  • Extraction is a batch job, not an interactive one. High effort by default, minutes per run on a real area. Unchanged areas are skipped entirely, the instruction prefix is cached, and both models and effort are per-stage settings.
  • Knowledge goes stale. Every fact records the source hash and commit it came from, status reports the drift, and CI should re-extract changed areas on merge — so drift is visible rather than silent.
  • Someone has to review what was generated. That is why it lives in git. The first wrong answer a customer sees costs more trust than the tool earns in a month.
